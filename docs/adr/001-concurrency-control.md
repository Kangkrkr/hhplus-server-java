# ADR 001: 동시성 제어 (주문 및 쿠폰 발급)

- **상태**: 채택 (Accepted)
- **날짜**: 2025-11-10

## Context (맥락)

- **문제**: 다수의 사용자가 동시에 상품을 주문하거나 쿠폰을 발급받을 때, 재고 및 잔여 수량의 정합성이 깨질 수 있습니다 (Race Condition). 예를 들어, 재고가 1개 남은 상품에 대해 두 명의 사용자가 동시에 주문을 요청하면, 두 건의 주문이 모두 성공 처리될 수 있습니다.
- **요구사항**: 어떤 상황에서도 재고 및 쿠폰 수량은 정확하게 관리되어야 하며, 사용자에게 잘못된 주문 경험을 제공해서는 안 됩니다.

## Decision (결정)

- **Redis의 Atomic-Operation (`INCR`/`DECR`, `DECRBY`)을 활용**하여 재고 및 쿠폰 수량을 관리합니다.
- 주문 프로세스는 다음과 같이 진행됩니다.
  1. Redis에서 재고를 먼저 차감한다.
  2. 재고 차감에 실패하면(음수가 되면) 즉시 주문을 실패 처리하고, 재고를 다시 복구한다.
  3. 재고 차감에 성공하면 다음 결제 단계를 진행한다.
  4. 결제 단계에서 실패할 경우, 차감했던 재고를 다시 복구한다 (Compensation Transaction).

## Consequences (결과)

### 긍정적 측면
- **성능**: In-memory 기반의 Redis는 RDBMS보다 월등히 빠른 속도로 Lock 및 수량 체크가 가능하여, 트래픽이 집중되는 주문/쿠폰 기능의 병목 현상을 최소화할 수 있습니다.
- **구현 단순성**: Redis의 원자적 연산을 사용하면 어플리케이션 레벨에서 복잡한 분산 락(Distributed Lock)이나 재시도 로직을 구현할 필요가 줄어듭니다.
- **확장성**: DB에 직접적인 부하를 주지 않으므로, API 서버와 DB 서버의 확장이 용이합니다.

### 부정적 측면
- **데이터 동기화**: Redis의 데이터와 DB의 데이터 간의 일시적인 불일치가 발생할 수 있습니다. 이를 해결하기 위해 주기적으로 데이터를 동기화하거나, 모든 데이터 변경 흐름이 Redis를 거치도록 강제해야 합니다.
- **인프라 복잡도**: Redis라는 별도의 시스템을 도입하고 운영해야 하므로 인프라 관리 포인트가 늘어납니다.
- **단일 실패 지점(SPOF)**: Redis 클러스터나 복제(Replication) 구성을 하지 않을 경우, Redis 장애가 전체 주문 시스템의 장애로 이어질 수 있습니다.
