# ADR 002: 비동기 처리 (외부 시스템 연동)

- **상태**: 채택 (Accepted)
- **날짜**: 2025-11-10

## Context (맥락)

- **문제**: 주문 완료 후, 실시간으로 주문 정보를 데이터 분석 플랫폼으로 전송해야 합니다. 만약 이 외부 플랫폼 API 호출이 동기적으로 처리될 경우, 외부 시스템의 응답 지연이나 일시적인 장애가 전체 주문 프로세스의 성능과 안정성에 직접적인 영향을 미칩니다.
- **요구사항**: 외부 시스템의 상태와 무관하게 사용자의 주문 요청은 빠르고 안정적으로 처리되어야 합니다. 주문 데이터는 유실 없이 안정적으로 외부 플랫폼에 전달되어야 합니다.

## Decision (결정)

- **Message Queue (Kafka, RabbitMQ 등)를 도입**하여 주문 정보 전송을 비동기적으로 처리합니다.
- 주문 API 서버는 `Producer`로서 주문 성공 시 메시지 큐에 주문 데이터를 보내는 역할만 수행합니다.
- 별도의 `Consumer`(Worker) 프로세스가 메시지 큐로부터 데이터를 받아 외부 데이터 플랫폼으로 전송합니다.

## Consequences (결과)

### 긍정적 측면
- **응답성 향상 (Decoupling)**: 주문 API는 메시지 큐에 데이터를 전송하는 즉시 사용자에게 응답을 반환할 수 있어, 외부 시스템의 상태와 무관하게 빠른 응답 시간을 보장합니다.
- **안정성 및 탄력성**: 외부 플랫폼이 일시적으로 장애 상태이더라도 메시지 큐가 데이터를 안전하게 보관(Durable)하고 있다가, 시스템 복구 시 Consumer가 재처리하여 데이터 유실을 방지합니다. 이를 통해 시스템 간의 결합도를 낮추고 장애 전파를 막습니다.
- **확장성**: 데이터 처리량(Throughput)이 증가할 경우, Consumer 프로세스의 수를 늘리는 것만으로 간단하게 시스템을 확장(Scale-out)할 수 있습니다.

### 부정적 측면
- **데이터 일관성**: 실시간 동기 방식에 비해 데이터가 외부 플랫폼에 반영되기까지 약간의 지연이 발생합니다.
- **인프라 복잡도**: 메시지 큐 시스템을 구축하고 운영해야 하므로 전체 아키텍처의 복잡도가 증가합니다.
- **메시지 관리**: 메시지 순서 보장, 중복 처리, 실패한 메시지 관리(Dead Letter Queue) 등 메시지 큐 운영을 위한 추가적인 정책 수립이 필요합니다.
