## 구성 요소 및 선택 이유

| 구성 요소 | 기술 스택 예시 | 역할 및 선택 이유 |
| --- | --- | --- |
| **DNS** | AWS Route 53 | **역할**: 도메인 이름을 IP 주소로 변환합니다.<br>**이유**: 안정성과 확장성이 검증되었으며, AWS 생태계의 다른 서비스(ALB, CloudFront 등)와 통합이 용이합니다. |
| **Load Balancer** | AWS ALB | **역할**: API 서버로 들어오는 트래픽을 분산하여 가용성을 높이고 서버 부하를 줄입니다.<br>**이유**: L7 로드 밸런싱을 통해 HTTP 헤더, URL 경로 기반의 유연한 라우팅이 가능하며, SSL 인증서 관리 및 Auto Scaling 연동이 편리합니다. |
| **API Server** | Spring Boot on EC2 | **역할**: 비즈니스 로직을 수행하는 어플리케이션 서버입니다.<br>**이유**: Auto Scaling Group으로 구성하여 트래픽 양에 따라 인스턴스를 탄력적으로 조절할 수 있어 비용 효율적이고, 장애 발생 시 자동 복구(Self-healing)가 가능합니다. |
| **Database** | AWS Aurora (MySQL 호환) | **역할**: 주문, 사용자, 상품 등 핵심 데이터를 영구 저장합니다.<br>**이유**: MySQL과 호환되면서 더 높은 성능과 가용성을 제공합니다. 읽기 전용 복제본(Read Replica)을 통해 읽기 성능을 쉽게 확장할 수 있습니다. |
| **Cache** | Redis (ElastiCache) | **역할**: 재고/쿠폰 수량 관리, 인기 상품 데이터 캐싱, 사용자 세션 등을 관리합니다.<br>**이유**: In-memory 기반으로 매우 빠른 데이터 액세스 속도를 제공하며, Atomic 연산을 지원하여 동시성 제어에 유리합니다. |
| **Message Queue** | Kafka / RabbitMQ | **역할**: 주문 데이터를 외부 플랫폼으로 비동기 전송하여 시스템 간 결합도를 낮춥니다.<br>**이유**: 대용량의 실시간 데이터를 안정적으로 처리할 수 있으며, 특정 컴포넌트의 장애가 다른 시스템으로 전파되는 것을 막아 시스템 전체의 안정성을 높입니다. |

## 배포 및 운영 전략

- **CI/CD Pipeline**: `GitHub Actions` -> `AWS CodeBuild` -> `AWS CodeDeploy`
  - Git-flow 브랜치 전략을 사용하여 `main` 브랜치에 머지(Merge)가 발생하면 파이프라인이 자동으로 실행됩니다.
- **배포 전략**: **Blue/Green 배포**
  - 무중단 배포를 위해 신규 버전(Green)을 먼저 배포하고, Load Balancer를 통해 트래픽을 점진적으로 전환합니다.
  - 배포 후 문제가 감지되면 즉시 구버전(Blue)으로 롤백하여 장애 시간을 최소화합니다.
- **모니터링 및 로깅**:
  - **모니터링**: Prometheus와 Grafana를 사용하여 서버의 핵심 지표(CPU, Memory, JVM)와 어플리케이션 지표(API 응답 시간, 에러율)를 시각화하고 임계치 기반의 알림을 설정합니다.
  - **로깅**: ELK Stack을 구축하여 분산된 서버 환경의 로그를 중앙에서 수집하고 검색/분석합니다.
